What it is — in plain English

No jargon required.

Modern LLM APIs let you cache a long conversation prefix: you pay full price to process it once, then a tiny fraction of that price on every later turn that re-uses it. It is how a long coding session stays cheap turn after turn.

The catch: the cache only remembers your prefix for a short while after the last use. Step away for a coffee, come back six minutes later, and the cache has forgotten everything. Your next turn has to re-process the entire prefix at full price — as if you had never cached it at all.

prompt-cache-keepalive sends a tiny "touch" request every few minutes while you are idle. Each touch re-uses the cached prefix, which resets the forget-timer, so the prefix stays warm and your next real turn is cheap. It is a heartbeat that keeps the cache alive between your messages.

A touch is a minimal request that re-uses the cached prefix. Re-using the cache counts as a read, and a read resets the timer — so the prefix never goes cold and the next real turn never pays the full re-processing price.

The mechanic — a wake under ~270 seconds

Anthropic's prompt cache has a ~5-minute (300-second) idle timer that slides forward every time the prefix is used. So the rule is simple: touch the cache at least once inside every 300-second window and it never expires.

In practice you touch a little early — the default is every 270 seconds (300 minus a 30-second safety margin) — so that even a slow request still lands inside the window. If you run an autonomous loop or scheduler instead of waiting on a person, the same idea is a sub-270s wake: schedule the next iteration less than 270 seconds out and the loop itself re-uses the cache, so it never crosses the eviction line.

without keepalive with keepalive ───────────────── ────────────── turn ─[ cache written ] turn ─[ cache written ] · idle 6 min ♥ touch (every 270s) ✗ cache forgotten ♥ touch prefix stays warm resume ████ full re-process resume ─[ cache read ] ~110,000 tok-equiv ~8,800 tok-equiv
The core insight. Autonomous loops should pace sub-270s wakes (or a keepalive touch) during idle. Because the prompt cache has a ~5-minute (300s) TTL, a wake under ~270s keeps the prefix warm and the next turn reads cache instead of re-creating it.

When it pays — the 17.4% breakeven

A touch is not free. Re-using the prefix costs roughly a tenth of writing it fresh, but ten such touches over a long quiet stretch add up. So when is the heartbeat actually worth it? This package ships a cost model that answers honestly — including when the answer is "don't bother".

The plain-English version

Every idle gap is a small bet. You pay for the touches now, during the idle. The payoff only arrives if the session resumes — that's when a warm cache saves you the full re-processing cost. If the session never comes back, the touches were wasted.

So you weigh two things: the cost of the touches against the re-processing cost you avoid when you do resume, scaled by how likely a resume is. Below about a 17.4% chance of resuming, the touches cost more than they save on average — skip the keepalive. Above 17.4%, the heartbeat pays for itself. Most real coding sessions resume far more often than 1-in-6, so for them keepalive is an easy win.

The arithmetic, for one idle gap

Let R be the cost to re-process the prefix on a cold resume, c the cost of one touch (a single cache read), and n the number of touches during the gap. The expected saving, for a resume probability p:

net_savings(p) = p × (R − c) − n × c

The break-even point is where that equals zero, giving the threshold probability:

p* = n × c ÷ (R − c)

For a typical 88,000-token prefix on Anthropic's pricing (write 1.25×, read 0.10× the base input price), a 9-minute idle incurs 2 touches, and:

p* = (2 × 8,800) ÷ (110,000 − 8,800) = 17,600 ÷ 101,200 ≈ 0.174

The library caps the number of touches (default 12) near the point where they would cost as much as a single re-write. So a session that goes quiet for an hour can't bleed tokens forever — the heartbeat stops and lets the cache expire. No silent waste, and the model tells you the threshold for your own numbers.

Quickstart

Zero dependencies. The core never imports an LLM SDK — you inject the touch.

Install

pip install prompt-cache-keepalive

Keep a cache warm

from prompt_cache_keepalive import (
    PromptCacheKeepalive, KeepaliveConfig, TouchResult,
)

# You inject the touch — the library owns only the timing + the spend cap.
def touch() -> TouchResult:
    resp = client.messages.create(
        model="claude-opus-4-8", max_tokens=1,
        system=SYSTEM,                                # last block: cache_control
        messages=PREFIX + [{"role": "user", "content": "."}],
    )
    u = resp.usage
    return TouchResult(ok=True,
                       cache_read_tokens=u.cache_read_input_tokens,
                       output_tokens=u.output_tokens)

keepalive = PromptCacheKeepalive(
    touch, KeepaliveConfig(ttl_seconds=300, margin_seconds=30),
)
keepalive.run(is_active=lambda: session_still_open())  # touches every 270s while active

Prove it pays for your numbers

from prompt_cache_keepalive import (
    CacheEconomics, net_savings, breakeven_resume_probability,
)

econ = CacheEconomics(prefix_tokens=88_000)
net_savings(econ, idle_seconds=540, interval_seconds=270,
            max_touches=12, resume_probability=1.0)
# -> 83_600.0    saved on a 9-minute idle that resumes

breakeven_resume_probability(econ, 540, 270, 12)
# -> 0.174       keepalive wins whenever resume is >17.4% likely

For autonomous agents

If you control the request loop, you don't even need a separate touch — schedule the next iteration sub-TTL. KeepaliveConfig.interval() gives you the number of seconds to wait (270 by default): wake inside that window and the loop re-uses the cache on its own.

Two layers, used together

Keepalive — prevent the miss

A timed heartbeat keeps the prefix warm so a resume is a cheap cache read, not a full re-write. Bounded by a spend cap so it can never waste tokens on a dead session.

Compaction — cheapen the miss

For the misses that slip through (first run, keepalive not yet started), compact_prefix shrinks what the provider must re-process — roughly a 4× reduction on a typical 88k prefix — while keeping the system prompt and the most-recent turns byte-identical.

Both are pure-stdlib and network-free, so they unit-test with zero network and handle no secrets. Full API, honest limitations, and at-scale math are in the README.
